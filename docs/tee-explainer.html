TEE 到底在做什么：名词 + 流程，深入浅出

给不想啃规范的人。先给直觉，再逐个拆名词，最后把"验证一台中转不记录你数据"的完整流程走一遍。

00一分钟直觉

把 enclave 想成放在一栋你不信任的大楼里的一个防拆玻璃箱。CPU 保证：楼里任何人（房东=云厂商、保安=运维、拿到万能钥匙的人=root）都看不进箱子、也改不了箱内的东西。 更关键的是远程证明：在你把信投进箱子之前，箱子会先递给你一张由 Intel 亲笔签名的"箱内物品公证照"——照片显示箱里装的正是那份公开、可复现、"看完即焚不留底"的代码。你核对无误，才把信封好投进去；照片对不上，就拒绝投递。
1保密：箱内数据连房东/root 都看不到（内存加密）。
2可证：箱子能出示"我装的是哪份代码"的硬件签名证据（远程证明/度量值）。
3先验后发：你先验证、密封给这个箱子，明文只在箱内出现一瞬——但只覆盖中转这一跳，上游厂商仍看到明文。

01名词表

▍硬件层 · 箱子本身
TEE 可信执行环境Trusted Execution Environment
CPU 硬件划出的隔离区，里面的代码和数据即使对操作系统/虚拟化层/物理机 root 也保密、防篡改。
对我们：就是那个"防拆玻璃箱"，让运营方在物理上也读不到 prompt。
Intel TDXTrust Domain Extensions
Intel 的 TEE：把一整台虚拟机作为受保护单元（Trust Domain），内存由 CPU 加密、与 hypervisor 隔离。
对我们：选它是因为可以整机 lift-and-shift——普通 Go 程序不改代码就跑进去。（对比 SGX 只保护进程内一小块，要改造代码。）
内存加密memory encryption
RAM 被 CPU 用宿主拿不到的密钥加密。
对我们：root 去 dump 内存、翻 swap，看到的都是密文。
度量值measurement · MRTD / RTMR
对"箱里到底启动了哪份代码+配置"做的密码学哈希指纹。MRTD=启动时的固定度量，RTMR=运行期追加的度量。
对我们：客户端 pin 住一个"已发布的无日志代码"的度量值；对不上就拒发。改一行代码→度量值就变。
TCBTrusted Computing Base
被信任的硬件/固件/微码版本集合；证明里带 TCB 状态。
对我们：可以拒绝"固件过期/有已知漏洞"的机器。
▍证明层 · 那张"公证照"
远程证明Remote Attestation
enclave 产出一份硬件签名的证据，证明自己的度量值；远端可离线核验。
对我们：整套信任的锚——用户"发送前"就能验"跑的是不是那份不记录的代码"。
Quoteattestation quote
那份签名证据本体，含度量值、report_data、签名链。
对我们：GET /attestation 返回的就是它。
report_datareport data (64B)
调用方可自定义、被"烤进"quote 的 64 字节。
对我们：放 H(nonce ‖ 临时公钥)——一举绑定新鲜性（防重放）和信道密钥。
DCAP / PCCS / Intel PCSData Center Attestation Primitives
离线验证 quote 的工具链：quote 的签名链到 Intel 根证书（PCK 证书由 Intel PCS 签发；PCCS 是缓存这些证书的区域服务）。
对我们：阿里云/GCP 给的是裸 Intel-rooted quote，客户端用 DCAP 验到 Intel——信任根是硬件厂商，不是云。
MAA / Nitro / SEV-SNP（对比项）other roots
Azure MAA=微软签的证明；AWS Nitro=AWS 签、enclave 模型；AMD SEV-SNP=AMD 的整机 TEE。
对我们：信任根落在云/别家厂商，叙事弱于裸 Intel DCAP。
▍通信与密钥层 · 怎么把信安全投进箱子
RA-TLSRemote-Attestation TLS
把 quote 塞进 TLS 服务器证书扩展——验证 TLS 证书 == 验证 enclave。
对我们：把"安全信道"和"被证明的代码"绑成一件事。
HPKEHybrid Public Key Encryption · RFC 9180
用对方公钥把数据"密封"，只有持私钥方能开。
对我们：客户端把 prompt 密封给 enclave 的被证明过的公钥——只有箱内能解。
密封 / 安全密钥释放sealing · Secure Key Release (SKR)
一个密钥只在"度量值符合策略"的 enclave 里才被 KMS 解封/释放。
对我们：上游 key 只对"被证明的无日志代码"释放明文——这就是 BYOK 里你敢把 key 给我们、而我们看不到的原理。
KMS / KBSKey Management / Broker Service
执行 SKR 的服务；master 常驻 HSM。
对我们：阿里云需自建一个小 KBS（验 quote→放 key），已被 kms.KeyProvider 接口隔离。
▍信任基础设施层 · 让别人也能核对
可复现构建reproducible build
同一份源码→逐位相同的二进制→相同度量值。
对我们：第三方能重建并确认"这个度量值 == 这份开源不记录代码"。没有它，开源也白开。
透明日志transparency log · Rekor/Trillian
公开的 append-only 日志（Merkle 树），可证 inclusion。
对我们：签名回执入日志→事后可查、丢弃/篡改会被发现。
fail-closedfail-closed
验证不过就拒绝，而不是"出错就放行"。
对我们：度量值/签名/nonce 任一不符，客户端绝不发送。
侧信道 / 缓存计时side channel · cache-timing
通过共享资源（如缓存耗时）间接泄露信息。
对我们：共享号池的跨租户缓存命中是已知侧信道，-isolated 把租户折进路由指纹以关闭它。

02流程一：远程证明握手（发 prompt 前）

客户端要证明 GET /attestation?nonce=<随机>
防住：重放攻击
enclave 生成一次性密钥 + 出 quote quote 里 measurement + report_data=H(nonce‖临时公钥)，由硬件签名。
客户端三验 ① 签名链到 Intel 根（DCAP/PCCS）；② measurement==注册表已发布值；③ report_data 对得上 nonce+公钥。
防住：假冒中转 / 换了带日志的代码 / 重放
任一不符 → fail-closed 直接拒发，明文一个字都不出用户设备。
密封发送 HPKE 把 prompt 封给被证明的公钥 + 能力令牌一起发。只有箱内能解。
enclave 内处理 RAM 内解密→亲和路由→SKR 取上游 key→转发→回封响应 + 签名回执。
客户端验回执 验签名 + measurement + model==请求（防降级）；可选查透明日志 inclusion。
防住：偷偷降级模型 / 伪造转发记录

03流程二：BYOK 密钥密封（你敢给 key、我们却看不到）

客户先验 attestation 确认对面是"被证明的无日志代码"，再托付。
把自己的上游 key 密封 用 KMS/enclave 公钥加密，绑定策略"只对度量值 X 释放"。
上传密文到控制面 New API 只存密文；运维/DBA/宿主机看到的都是密文。
请求时 KMS 门控释放 KMS 验实时 quote+度量值达标→把 key 解给这个 enclave，仅存 RAM。
结果 你（公司/运维）永远看不到明文 key，也看不到 prompt。这就是"密钥方与运营方分离 / operator-blind"。

04常见误解

✕
"用了 TEE，OpenAI 就看不到我的数据了。"→ 不对。只保护中转这一跳；prompt 仍以明文交付你选的上游，受其自身条款约束。
✕
"中转说它用了 TEE，所以安全。"→ 不对。必须你自己（或你的软件）去验证 attestation，最好客户端侧、开源 SDK。被验证方自己控制验证器=没验证。
✕
"这靠区块链/零知识证明实现。"→ 不对。这是 TEE + 远程证明。ZK 管"算得对不对"（完整性），不管"数据不被留存"（隐私），且当前跑不动大模型。
✕
"这是端到端加密。"→ 只在客户端↔enclave 之间端到端；enclave 之后到上游是普通 TLS，上游看到明文。
