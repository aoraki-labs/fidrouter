00一分钟直觉

enclave = 放在一栋你不信任的大楼里的防拆玻璃箱。CPU 保证楼里任何人（云厂商/运维/root）都看不进、改不了箱内。发信之前，箱子先递给你一张由 Intel 签名的"箱内物品公证照"——证明装的正是那份公开、可复现、"看完即焚不留底"的代码。核对无误你才把信密封投进去；对不上就拒发。明文只在箱内出现一瞬——但只覆盖中转这一跳，上游厂商仍看到明文。

·现状 · BYOK 真 Claude 已在 Confidential Space 端到端跑通

Live：GCP Confidential Space · Intel TDX。度量值 = 我们容器的 image_digest（不再只是基础 VM）。客户端验度量值 pin + 证明签名 + eat_nonce 绑定 → attested E2EE → enclave 内注入 BYOK 上游 key → 直连 api.anthropic.com（路由 B：prompt 不过控制面） → 真 Claude 回答 + 签名回执（防降级）。一条命令 deploy/gcp/use.sh "你的问题"。

01各方关系：谁是谁、谁信谁、谁付谁

终端用户

带来：prompt + 对隐私的疑虑。
关系：用 verify SDK 自己验证 enclave，不信中转的口头承诺。
付费：对 SDK 不付费。

应用方 / BYOK 客户

放弃自建中转、只有"用户渠道"的一方：有用户+上游 key，但不想搭中转基建。带来：用户 + 密封的 key。关系：把 key 密封给我们、用我们当可验证中转。付费：给我们（服务费/订阅）。

fidrouter（我们）

身份 A=可验证中转（管道，向客户收费）；身份 B=中立验证层/公证方（非管道，向合作中转收费）。运营 enclave + 注册表 + 透明日志 + 免费 SDK。

合作中转站

已有自己的用户与号池。关系：跑我们的被度量镜像、进我们的注册表，换"可验证"背书。付费：给我们（认证/分成）。

上游厂商

OpenAI/Anthropic/Gemini，做真正推理。关系：在信任边界之外——看到明文，受其自身 ZDR 条款约束，我们证明不了它。

云 + Intel（TEE 根）

阿里云/GCP 提供 TDX 机密 VM；Intel 是远程证明的信任根。关系：用户信的是 Intel 硬件 + 公开度量值，不是云厂商、也不是我们。
一句话关系链：用户 →(验证)→ enclave；用户信的是 Intel 根 + 公开注册表，不是中转的自述。应用方/合作中转 →(付费)→ 我们；我们 →(部署在)→ 阿里云/GCP TDX、→(把信任根锚在)→ Intel、→(公示到)→ 注册表/透明日志。所有人 →(转发)→ 上游（明文，超出可证范围）。

04一次请求 = 一次远程证明握手

认证拿能力令牌 客户端 → 控制面，得签名 JWT（租户/模型白名单/配额）。
要证明 GET /attestation?nonce=<随机>
防：重放
enclave 出 quote 含 measurement + report_data=H(nonce‖临时公钥)，硬件签名。
客户端三验 ①签名链到 Intel 根；②度量值==注册表已发布值；③report_data 对上 nonce+公钥。
防：假冒中转 / 换带日志代码 / 重放
不符 → fail-closed 拒发，明文不出设备。
密封发送 → enclave 内处理 HPKE 封给被证明公钥；RAM 内解密→亲和路由→KMS 门控取上游 key→转发。
签名回执 + 客户端复验 回执含 model==请求，客户端验签+度量值；可选查透明日志。
防：偷偷降级模型 / 伪造记录

05BYOK 密钥密封（你敢给 key、我们却看不到）

客户先验 attestation 确认对面是被证明的无日志代码，再托付。
密封自己的上游 key 用 KMS/enclave 公钥加密，绑定"只对度量值 X 释放"。
上传密文到控制面 只存密文；运维/DBA/宿主看到的都是密文。
请求时 KMS 门控释放 验实时 quote+度量值达标→解给该 enclave，仅存 RAM。
结果 = operator-blind 你（公司/运维）永远看不到明文 key，也看不到 prompt。

06两条合作流程

A · 应用方/BYOK 客户接入（我们当中转 = 身份 A）

验 attestation 客户确认我们是被证明的无日志中转。
密封上传 key 或用我们的托管号池（先行）。
发子令牌给它的用户/应用 配额/模型白名单，用户拿不到原始 key。
用户走 verify SDK 默认验证 + 密封；拿回执。
计费/审计 从回执计费；客户对它的用户可证明"我们读不到"。

B · 中转站接入（我们当验证层 = 身份 B）

拉可复现镜像 在它自己的 TDX 里跑我们的被度量 fid-proxy。
登记 + 发布度量值 注册 CP 公钥，度量值进我们的注册表。
回执灌透明日志 供任何人事后核验。
拿"Verified by fidrouter"徽章 它的用户用统一 SDK 验证它。
按验证请求分成 / 认证费 SDK 对终端用户仍免费。

07TEE 名词速查

TEE 可信执行环境Trusted Execution Environment
CPU 划出的隔离区，对 OS/hypervisor/root 都保密防篡改。=防拆玻璃箱。
Intel TDXTrust Domain Extensions
把整台 VM作为受保护单元，内存 CPU 加密。可整机 lift-and-shift，Go 不改代码。
度量值measurement · MRTD/RTMR
"箱里启动了哪份代码"的哈希指纹。客户端 pin 它，改一行代码就变。
远程证明Remote Attestation
enclave 出硬件签名证据证明自己的度量值。整套信任的锚。
Quote / report_dataattestation quote
签名证据本体；report_data 我们放 H(nonce‖公钥)。绑新鲜性+信道密钥。
DCAP / PCCSIntel PCS 链
离线验 quote，签名链到 Intel 根。信任根是硬件厂商不是云。
RA-TLS / HPKERFC 9180
把 quote 绑进 TLS 证书 / 用被证明公钥密封数据。只有箱内能解。
密封 / SKRSecure Key Release
密钥只对度量值达标的 enclave 释放。BYOK operator-blind 的原理。
可复现构建reproducible build
同源码→逐位相同→同度量值。没它，开源也白开。
透明日志 / fail-closedRekor · default-deny
回执入公开 append-only 日志；验不过就拒发。事后可查 + 默认拒绝。

完整定义见 docs/WHITEPAPER.md。

09终端用户怎么相信某中转真用了 fidrouter

核心：信任必须由用户一方执行或可被与中转无关的第三方核对；被验证方控制验证器=没验证（同 TLS）。

级别机制信任来源
0 无效中转官网写"无日志"口头，等于没有
1 主机制用户侧跑开源 verify SDK，发送前验证 fail-closed用户自己机器上的代码
2 事后可证enclave 签名回执 + 公开透明日志用户/审计者事后可验，含防降级
3 中立第三方我们域名的验证页/注册表，独立 monitor 持续证明查我们的站，不查中转自述（类 CA）
兜底消费级 App：集成方默认开验证+透传"✓已验证"徽章验证成为默认路径
隐藏风险：中转自派改过的客户端在封装前偷明文→架空 L1。对策：SDK 开源+用户侧运行+L2/L3 与中转无关的二次核对。边界同 TLS：只保护真正验证的用户。

10能证明 / 不能证明

✓
这台中转不记录/不留存/不外泄你的 prompt，且跑的确是那份开源代码
✓
prompt 只能在被证明的 enclave 内解密
✓
路由真实性：回执证明服务的就是你请求的模型
✕
不能证明 上游拿到明文后怎么处理
!
必带限定：仅覆盖中转这一跳，上游受其自身 ZDR 条款约束
✕
不能说"端到端加密 / 零知识私密推理"

11开源边界（可验证性的前提）

必须开源 + 可复现构建

数据面 fid-proxy、verify SDK、构建/度量流水线。证明只说"运行代码==度量值 X"；X 源码保密则无法确认它不记录=可验证性归零。Apache-2.0。

不必开源

控制面/计费/路由策略/后台——不碰明文、不在度量值内。开源数据面是信任前提不是让利；壁垒在验证网络与合规。

12商业模式

① BYOK（首推）

客户密封自带 key，operator-blind。规避转售合规。客户=放弃自建中转、只有用户渠道的应用方。

② 企业订阅

Team/Business/Enterprise 三档：专属 enclave、数据驻留、等保信创审计。最高毛利。

③ 验证层（Path A）

向合作中转收认证/分成；SDK 免费。我们当公证方，非管道。

壁垒不是 TEE 本身（可 fork）。是中立第三方可验证性=注册表+可复现构建+透明日志+被广泛信任的 verify SDK 构成的双边信任网络 + 合规 + 先发。"只是管道"是要避免的低毛利陷阱。
